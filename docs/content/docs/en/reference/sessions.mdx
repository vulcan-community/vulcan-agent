title: Sessions & conversations
description: The two-layer identity model — a stable conversation pointer in front of rotatable JSONL transcripts.
---

Vulcan separates **conversation** (the stable external address) from **session** (a concrete transcript). The split lets `/new` start a fresh transcript without losing the caller's identity, lets `/resume` flip back to an older transcript, and keeps the runtime binding on the session it belongs to.

## Conversation vs session

A **conversation** is the user-facing address that persists across `/new`:

- Feishu — the chat's `chat_id`.
- HTTP — the `X-Conversation-Id` request header (defaults to `"default"` when omitted).

A **session** is one concrete transcript — a pair of files (`<session_id>.jsonl` + `<session_id>.meta.json`) keyed by a random 12-hex-char id. Rotating the conversation's pointer to a new session is how `/new` works; repointing it to an existing session is how `/resume` works. The old session stays on disk, unchanged.

## File layout

```
~/.vulcan/sessions/
├── <channel_id>/
│   ├── _conversations/
│   │   └── <conversation_id>.json     # {"current_session_id": "..."}
│   ├── <session_id>.jsonl             # transcript (one SessionItem per line)
│   └── <session_id>.meta.json         # {"runtime_name": "...", "conversation_id": "..."}
```

`<channel_id>` is the transport name — `gateway` for the HTTP API, `feishu` for Feishu, and so on. Conversations and sessions never cross channel boundaries; the same id in two channels is two separate pairs of files.

## Session id format

Generated by `uuid.uuid4().hex[:12]` — 48 bits of randomness encoded as 12 lowercase hex chars (e.g. `9f2a1c4b6e0d`). The space is large enough that collisions are not a concern for a single-user deployment, and short enough that the id fits in a CLI message.

## Pointer file — `_conversations/<conversation_id>.json`

One field:

| Field                | Type   | Description                                                               |
| -------------------- | ------ | ------------------------------------------------------------------------- |
| `current_session_id` | `str`  | The session the conversation is currently attached to.                    |

Touched only by `resolve_current_session` (first-touch install), `rotate_current_session` (the `/new` path), and `set_current_session_id` (the `/resume` path). The file's mtime is used by `/conversations` to sort rows newest-first.

## Session meta — `<session_id>.meta.json`

| Field             | Type   | Description                                                                                  |
| ----------------- | ------ | -------------------------------------------------------------------------------------------- |
| `runtime_name`    | `str`  | Which runtime this session is bound to. `/switch`, API `"model"`, and first-touch write it. |
| `conversation_id` | `str`  | Back-pointer to the owning conversation. Set at `create_session` time; not rewritten.        |

The `conversation_id` back-pointer is what lets `/sessions` and `/conversations` list the right rows without scanning every pointer file: they glob `*.meta.json` and filter.

## How each command touches storage

- **`/new`** — allocates a fresh session, writes its `.jsonl` + `.meta.json` (with the inherited `runtime_name`), and rewrites the `_conversations/<conversation_id>.json` pointer.
- **`/resume <session_id>`** — validates the target session's `meta.conversation_id` back-pointer matches the caller, then rewrites just the `_conversations/<conversation_id>.json` pointer.
- **`/switch <name>`** — resolves the conversation's current session id, then rewrites only that session's `.meta.json` (`runtime_name` field).

The three concerns live in three files on purpose: the transcript (`.jsonl`) is append-only, the runtime binding (`.meta.json`) rebinds on `/switch` and inherits on `/new`, and the conversation pointer (`_conversations/...`) rotates on `/new`/`/resume`. Each command touches exactly what it has to.
